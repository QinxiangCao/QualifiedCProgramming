# V2.2.0 版本更新与 Proof Port 指南

本文面向把旧版 C annotation、策略和 Rocq/Lean proof 迁移到 QCP v2.2.0 的使用者与 AI。本文沿用之前 Version_Log 的习惯，记录影响 proof port 的接口变化、实际修复方法和检查顺序。

V2.1.0 的架构参数化原则继续适用，见 [V2-1-0.md](V2-1-0.md)。本轮迁移还涉及函数规约语义、规约推导 VC、公共策略路径、存储接口，以及刷新目标后的 binder 和分支顺序。不能仅按旧 witness 名称复制 proof body。

## 1. 迁移前先固定生成环境和修改范围

升级时一起更新 binary、基础库、公共策略及其证明。当前预编译工具位于 `bin/windows/`、`bin/linux/`、`bin/macos-arm64/`、`bin/macos-x86_64/`，每个平台包含 `symexec`、`StrategyCheck`、`lsp`、`mcp` 和 `spec-check`；Windows 文件带 `.exe`。

推荐顺序：

1. 保存旧 C annotation、custom strategy、manual proof 和 case library，并记录生成参数、工作目录及所选 CRules。
2. 同步基础库和公共策略，用同一套新 binary 刷新生成文件。
3. 先解决前端、路径、类型或策略匹配错误，再编译 proof。生成失败时，旧的 goal 文件不能代表本轮生成结果。
4. 对失败 witness 比较新旧 statement，判断是接口变化、分支重排、auto/manual 分工变化，还是确实缺少证明。
5. 修改 manual proof、必要的 library 或已确认有问题的 annotation/strategy；后两类修改后重新生成。
6. 编译完整的 strategy check 和 VC check，再做目录或项目级检查。

保持原有函数契约和数学模型。不要通过加强前置条件、削弱后置条件、删除困难分支或新增公理来完成机械迁移。如果发现契约本身的问题，应单独说明并审查。

本仓库的 AI 单个 C 验证任务仍由 [AGENTS.md](../AGENTS.md) 指定的 verification-orchestrator 流程执行。本文提供判断方法，不替代 controller 的 action、允许修改范围和 final-check。

## 2. 生成文件、公共策略和证明头部

### 2.1 先更新公共策略，再刷新案例

非内置公共策略集中到 `QCP_examples/verification/`，对应 Rocq 路径为 `SimpleC.Verification`；内置规则快照位于 `QCP_examples/verification/builtin/`，对应 `SimpleC.Verification.BuiltIn`。

旧案例若还导入自己目录中的公共策略副本，应检查当前生成文件的 import 和 `VC_Correct` 所需接口，迁移到公共入口。不要同时加载旧副本和新快照，避免同名规则、module 或 proof field 冲突。

仓库级生成命令见 [docs/generation.md](../docs/generation.md)。以下命令从仓库根执行，Linux/macOS 使用 `dune`，Windows 使用 `./dune.cmd`：

```sh
# 更新内置规则快照及其生成证明，再编译快照。
dune build @gen-builtin --auto-promote
dune build -j4 Rocq/Verification/BuiltIn/

# 刷新项目 VC；已有 manual proof 按生成入口的保留规则处理。
dune build -j4 @gen-vcs --auto-promote
```

Dune 默认先展示生成差异，`--auto-promote` 才同步回源码。配置或 builtin exports 变化时，可能需要先 promote 再重新生成。普通 `dune build` 不会自动刷新全部 VC。目录布局变化后还要更新 Dune 配置，不能只替换 import 字符串。

`*_goal.v`、`*_proof_auto.v`、`*_goal_check.v` 及 Lean 对应文件应来自当前生成器，不应手改以适配旧 proof。`--proof-manual-as-template` 生成的是 `.v.in` 模板，不是已完成的人工证明。Dune/Python 生成入口会保留已有 manual；直接调用工具或局部 Makefile 时仍应核对覆盖行为并保留旧证明。

策略文件需要区分：builtin 导出证明由工具生成；项目自定义策略的手写证明需要随 strategy goal 一起迁移。不能因为文件叫 `*_strategy_proof.v` 就认定全部可覆盖或全部禁止修改。

### 2.2 使用公共 Prelude，保留案例自己的依赖

普通 VC 证明头部使用：

```coq
From SimpleC.Verification Require Import VCPrelude.
(* 接着导入当前案例的 goal、auto 和 case library。 *)
Import naive_C_Rules.
```

策略证明使用 `From SimpleC.Verification Require Import StrategyPrelude.`；关系程序规格所需公共依赖可使用 `SafeExecPrelude`。Prelude 替代的是公共 import 和 scope 声明，case library、当前 goal/auto module 和实际所选 CRules 仍须保留。

## 3. CRules、存储和数组接口

### 3.1 同名 `naive_C_Rules` 的语义已变化

`naive_C_Rules32/64` 与 `Snaive_C_Rules32/64` 现在基于 `FunAssertion.SL`。`naive_C_Rules` 是当前 32 位入口；旧 `ConAssertion` 实例改名为 `naiver_C_Rules32/64`，旧的 `Snaive_C_Rules` 别名已移除。

新模型包含内存和函数环境。直接展开旧 assertion model、手工构造旧 state 或假定 state 只有内存的库证明需要重新检查；优先通过公开的分离逻辑接口推导。普通案例不能仅为恢复旧 tactic 而改用 `naiver_C_Rules32`，否则可能与新生成 goal 的语义实例不一致。

`*_def.v` 也遵循所选 CRules 和 `--no-CRules` 设置。若普通 store、array 谓词看起来相同却不能匹配，先检查 goal、definition、library 和 manual 是否使用同一个规则模块。

### 3.2 存储值类型由 C 类型决定

| 旧写法或假设 | 当前迁移方式 |
| --- | --- |
| `PTR(T)` | 改为 `PTR`；指针目标类型不再作为该存储类型的参数 |
| 所有 `poly_store` / 通用 `store` 的值都标为 `Z` | 按当前 C 类型的值类型绑定；策略可用 `front_end_type_value(ty)` |
| `store_struct` | 使用通用 `store` 接口，并核对生成的结构体定义 |
| 直接展开旧字节存储包装 | 使用当前 `store_bytes`、`store_bytes_Z`、`undef_store_bytes` 及配套引理 |
| 依赖 `simpl` 展开公开 store 或 `sizeof(...)` | 使用公开资源引理和相应 tactic；必要时只在 proof 局部正规化 |
| pointer 大小恒为 `4` | 使用当前架构的 `sizeof(PTR)`；32 位特例显式使用兼容引理 |

自定义架构或字节序模块也需对齐新接口：`CArchSig` / `CEndianSig` 保留参数和公理，共享定义与定理由 `CArch` / `CEndian` 提供。不要把旧模块整段复制到新签名下，再通过补公理绕过类型错误。

### 3.3 数组目标形状与边界

数组大小现在按“维度 × 元素大小”打印。旧证明可能使用交换后的乘法式、字面量大小或不同结合方式；先用局部 `replace ... by lia`、相应 `sizeof` 引理或架构 tactic 对齐，不要改基础库 statement 来适配单个 VC。

本版恢复 `missing_i` 与元素资源重组完整数组、完整范围 `seg` 匹配 `full` 的规则，同时移除了自动丢弃空片段和自动将前置元素并入片段的两条规则。因此刷新后多出一个空数组片段不一定是错误；应检查当前资源，再用对应数组引理消去或拼接。

数组模块已移除不必要的 `sizeA_valid` 前提。旧的实例构造或 positional lemma application 若报多余参数，应先查看当前签名。结构体只在实际需要数组表示时生成 ArrayLib 实例，不应为普通结构体补回旧版的额外义务。

Lean 的未初始化数组尾元素规则也已修正：半开区间 `[lo, hi)` 的末元素下标为 `hi - 1`。若旧证明使用 `hi`，必须同时核对索引、片段范围和边界前提，不能只靠改写掩盖越界。

## 4. Annotation 语义变化要先于 proof 修复

### 4.1 规约选择、类型实参和 `@pre`

未命名规约使用 `default`，同一函数不能有两个同名规约；显式 `default` 不能与未命名规约并存。未指定规约时优先选择 `default`，否则保留首个规约的选择方式。多规约调用建议显式选择，避免声明顺序变化影响迁移。

调用处类型实参从旧形式：

```text
where(spec) x = v ; A = Z
```

改为：

```text
where(spec) {A = Z} x = v
```

同一多态规约被多次实例化时，每次量词绑定独立刷新。遇到变量类型错位，应检查当前实例及其类型实参，不要依靠旧的内部变量 ID 或打印名称关联两个调用。

`x@pre` 现在表示当前函数规约为参数 `x` 绑定的逻辑变量，仅适用于函数参数。它不是任意程序状态快照。通用 `@mark` 和 `Given ... of mark` 已删除；中间状态值应使用当前支持的 Given/逻辑变量显式保存，不能把所有旧 mark 引用机械改成 `@pre`。

### 4.2 `which implies` 和分支合并

`which implies` 的前条件不再允许 `||`。旧版按位置配对的：

```text
P1 || P2 which implies Q1 || Q2
```

应根据实际执行分支分别写带 `$ branch` 的推导。单一前条件推出多分支后条件仍合法。推导在执行到该 annotation 时按当前规约和分支解释，旧 proof 可能因此获得不同的变量绑定或分支条件。

partial `Branch` 合并会检查存在变量的名称与类型、空间资源、局部变量和函数规约的一致性，只保留共同的纯事实。若失败源于分支私有变量逃逸或资源不一致，应修分支 annotation；manual proof 无法补回生成阶段已缺失的正确状态。

### 4.3 前端或策略错误不是 VC 证明失败

不可达语句也会经过语义检查；未声明变量、非法 `goto`、宏选择变化或混写的 `Extern Coq` 声明可能在生成 VC 之前失败。`::` 类型声明和 `:` 项声明应按诊断拆分。策略会检查未绑定的表达式、类型和 StoreCType 变量；应修正匹配分支及动作执行顺序。

复现时保留实际 `-I`、`-slp`、宏配置和原始诊断。旧的数字执行模式 `-s` 已移除，调试前端应使用当前支持的 `--syntax-only` 或相应 dump 选项，不能把旧命令失败误判为 proof 回归。

## 5. 函数指针与规约推导 VC

### 5.1 区分普通蕴含与独立规约推导

断言中的 `f |= ... Require ... Ensure ...`、抽象 `FpSpec` 及其 `which implies` 推导，现在完整参与相应断言的检查。普通蕴含中嵌入的函数规约不会被提前抽走；不能像旧 proof 那样假定只剩内存资源，直接 `cancel` 就结束。

显式的 `spec1 <= spec2` 声明仍产生独立规约推导义务。迁移时核对方向、输入实参、逻辑变量、frame 和后置条件，不要仅因为两个规约名字相近就复用旧证明。

### 5.2 返回值量词与分离蕴含的顺序

规约推导 VC 的字段名称和 statement 都可能变化。若当前返回值位于后置条件转换外层的全称量词中，就必须先引入该返回值，不能把它当成可任选的存在 witness。

例如，在前置条件和 frame 已处理完、目标右侧依次为返回值全称量词和分离蕴含时，证明步骤可以是：

```coq
Intros_r retval.
apply_sepcon_adjoint.
Intros val'.
Exists val'.
split_pure_spatial; [cancel | dump_pre_spatial; assumption].
```

若旧片段在 `apply_sepcon_adjoint` 后同时 `Intros val' retval`、再 `Exists val' retval`，就需要根据新的量词结构调整。上面的片段只示意这一种目标形状，末尾的资源消去和纯命题证明仍以实际目标为准。

迁移同类证明时，先在当前 goal 中找出全称返回值、源规约的存在量词、目标规约需要的 witness，以及 `-*` 两侧的资源，再安排 `Intros_r`、`apply_sepcon_adjoint` 和 `Exists`。不要只替换 lemma 名称而保留旧量词顺序。

## 6. witness 映射和 auto/manual 分工

### 6.1 按语义对齐，不按数字编号对齐

刷新后，相邻 `return_wit` 或 `entail_wit` 的顺序可能交换，多个规约对应的目标也可能重新排列。不同分支的前提和资源未必相同，不能仅凭编号对换 proof body 或 `Left` / `Right`。

为每个失败目标比较：规约名、分支条件、输入/输出对象、alias 条件、空间资源、量词顺序。先建立 old-to-current 映射，再迁移 proof body；split lemma、上层 `Goal_apply` 和 `VC_Correct` 导出也要同时对齐。

### 6.2 缺失或重复 field

`goal_check` 报 field missing 或 label already declared 时，先比较当前 `VC_Correct` 要求的字段和 auto/manual 实际导出的字段。

- auto 已提供同一义务时，删除 manual 的重复导出；保留同名 lemma 的两份实现不能解决接线问题。
- 如果一个字段重复而另一个缺失，先排查分支重编号。旧 proof body 可能属于缺失的那个义务，而不是应该直接删除。
- auto 和 manual 都缺失时，按当前 statement 补充证明，不修改 `goal_check` 隐藏缺口。

对于模块签名，`Axiom proof_of_...` 是等待实现的接口字段；它与实际证明实现中的未证明公理不同。检查时要看其作用域、实现和最终 check 接线，不能仅按文本中是否出现 `Axiom` 判断。

### 6.3 preprocessing 与引入 tactic

Rocq 的 `Intros` / `Intros_r`、`Exists` / `Exists_l` 已支持参数列表；`Intros` 和 `Intros_r` 还会检查相应位置是否确有量词。旧 tactic 在整个目标被意外展开后仍“匹配成功”的行为不能作为迁移依据。

先运行案例使用的 preprocessing，再区分纯命题、仍含资源的 entailment、已经闭合的目标。`No such goal` 往往表示后续脚本多余；找不到存在量词时，应先看它是否已经被引入，而不是继续展开整个语义模型。

`csimpl` 的 rewrite 搜索依赖新的 `logic_equiv` 实例导出。相同目标突然 typeclass 搜索缓慢或失败时，检查逻辑库与接口版本，尤其是 `LogicGenerator/demo932/Interface.v`，不要先增加搜索深度或复制局部实例。

## 7. Lean：同时迁移 binder 与调用实参

Lean 中 `intro` 的变量名按当前位置绑定。刷新后的量词顺序可能变了，即使原变量都是 `Int`，旧脚本也可能在较后位置才报错。

本次 [chinese_remainder_theorem_proof_manual.lean](../Lean/examples/SimpleC/EE/LLM_bench/Algorithms/chinese_remainder_theorem/chinese_remainder_theorem_proof_manual.lean) 的相关前缀由：

```text
moduli_pre remainders_pre n_pre moduli_l remainders_l ...
```

变为：

```text
moduli_l remainders_l n_pre remainders_pre moduli_pre ...
```

修复时既调整 `intro`，也调整上层证明对 split lemma 的显式实参顺序。只改 introduction 会留下 `Goal_apply` / `exact` 的位置参数错配。`PreH1` 等编号同样不稳定，应根据命题内容选择假设。

对已有 `Inhabited` / 默认值参数的目标，继续按当前生成签名检查实例绑定；不要为了匹配旧 proof 把生成的默认值改回硬编码值。空间目标还应核对函数规约、Bool 存储及多维数组的当前实例和 import。

先编译受影响 module，再编译对应 Lake package。使用仓库固定的 Lean toolchain；不要把另一仓库残留的 `.olean` 当成当前源码已经通过的证据。

## 8. SpecCheck 与证明编译分开检查

SpecCheck 检查声明一致性和覆盖关系，不运行符号执行或证明检查。JSON 中 `proofsChecked` 为 `false`；`VERIFIED` 表示规约具有实现声明或推导链覆盖，`ASSUMED` 表示匹配到显式外部契约。

符号执行可以在函数定义无 annotation、已有声明恰好给出一个规约时使用该规约；SpecCheck 不把这种隐式选择自动记为实现覆盖。若实现应使用已声明的默认契约，可在实现处添加 `/*@ default */` 显式选择它。其他命名契约也应选择正确的规约，不应为消除覆盖诊断而改动 Require/Ensure。

检查命令的基本形式如下，尖括号内容需替换为实际路径：

```text
spec-check <project-root> -I <include-dir> --json <report.json>
```

使用 `bin/` 中对应平台的程序，Windows 为 `bin/windows/spec-check.exe`。按真正的项目边界选择检查目录；独立实现中的同名函数不应互相提供覆盖。声明检查通过后，再运行该项目的完整 Rocq 或 Lean 证明构建目标。

确有外部原语时，可用 `--given-contracts <manifest.tsv>` 提供经审查的精确契约清单，不能用来豁免待证明算法。签名、规约或项目边界改变后应重新审查清单。

SpecCheck 和常规证明构建不会自动扫描所有 proof 中的占位或汇总证明闭合性：Rocq 的 `Admitted`、Lean 的 `sorry`、显式模型假设和 auto 模块内容需要另外检查。`goal_check` 编译成功与“无占位、无额外假设”是不同结论。

## 9. 常见错误的检查顺序

| 现象 | 优先检查 | 修复位置 |
| --- | --- | --- |
| 找不到公共策略 module，或同名 module 冲突 | 旧副本、新公共路径、`-I` / `-slp` 及构建配置 | annotation/import、生成配置 |
| store 或 array 看似相同却不能匹配 | CRules 实例、值类型、尺寸和地址正规化 | 公共库同步或 proof 局部 |
| derive VC 在 `Exists` / `Intros` 处失败 | 返回值是否已变成外层全称量词，`-*` 两侧资源 | manual 的规约推导证明 |
| `Cannot find ... equality`、`PreH` 类型不符 | binder 与假设顺序、当前规约和分支条件 | manual，不改 generated goal |
| `goal_check` 缺 field 或重复 label | auto/manual 导出集合与 witness 语义映射 | manual 导出或缺失证明 |
| Lean split lemma application 类型错位 | `intro` 与显式调用参数是否同步重排 | caller 和 callee proof |
| `No such goal` | 前一步是否已经闭合目标 | 删除多余 proof 步骤 |
| 空片段无法消去、数组尾下标不符 | 当前资源规则、半开区间边界 | 数组引理应用或确有错误的规则 |
| SpecCheck 报未覆盖但旧符号执行成功 | 实现处是否显式选择规约、推导来源是否正确 | C annotation，随后重新生成 |
| `csimpl` / typeclass 搜索异常 | Prelude、逻辑接口和子模块版本是否一致 | 依赖同步，必要时重编译 |

## 10. 跨仓库 port 和最终验收

democases 的库更新还需要同步到 `annotated_simplec` 与 `annotated_simplec_lean`。按逻辑模块对应关系迁移 `CoreLang`、`FunAssertion`、存储/数组接口、Prelude 和受影响示例；各仓库目录结构及构建入口不同，不能把整棵生成目录直接覆盖过去。

Rocq 侧同步时要检查 `sets`、`listlib`、`unifysl` 等实际子模块提交。当前 `annotated_simplec` 的 unifysl 更新已合入其上游仓库 `unifysl-prp` 的 `master`；父仓库记录具体提交并配置跟踪 `master`。只写 branch 名称不会自动更新已有 checkout 或父仓库 gitlink。

Lean 侧需要同步库源文件及相应 Lake 依赖、manifest、实例和导出；如果 builtin 策略快照名称与原始规则名不同，应检查生成器是否按 `qcp-builtin` 标记找到正确规则，不能手写空策略目标补缺口。

迁移完成至少确认：

1. 新 goal、auto、definition、strategy 和 check 来自一致的 binary、库与生成参数。
2. 当前 `VC_Correct` 及策略接口由实际实现覆盖，auto/manual 没有误重复或漏项。
3. 手工证明、案例 library、策略 proof 和最终 check 均编译通过；再检查相应 Rocq/Lake 项目。
4. 没有为了 port 改弱契约、删除真实义务、增加占位或绕过生成接口。
5. SpecCheck 结果、证明编译结果及假设/占位审查范围分别说明，不能互相替代。

本轮合并时完成了相关 Rocq、Lean 和两个 annotated 仓库的构建检查，但这不是对仓库所有历史 auto 内容或公理的整体审计。后来更换 binary、annotation 或依赖后，应针对新的文件重新验证，不能沿用旧日志声称本次 proof 已通过。

给 AI 执行具体 port 时，应同时提供 C/strategy、旧 manual、当前生成目标、失败上下文、完整生成命令和允许修改范围。最有用的依据是“同一个义务在新旧版本中的 statement 差异”，而不是单独一条报错或旧 lemma 名字。
