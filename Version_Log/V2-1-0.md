# V2.1.0 Proof Porting Guide

本文说明使用 QCP v2.1.0 的最新 binary 重新生成验证条件后，如何把旧版 Rocq/Coq proof 迁移到当前接口。前半部分记录 architecture-parametric `CRules` 带来的接口变化；后半部分说明 binary、symbolic execution 和 solver 更新后可复用的 proof repair 方法。

核心原则：

- `*_goal.v`、`*_proof_auto.v`、`*_goal_check.v` 和 strategy generated files 代表当前 binary 的输出接口，不应通过手工修改这些文件来迁就旧 proof。
- `*_proof_manual.v` 与必要的 proof library 应以当前实际 goal shape 为准；旧脚本只能作为证明思路的参考。
- `sizeof(INT)`、`sizeof(UINT)`、`sizeof(CHAR)` 等非 pointer 类型仍应保留原来的库接口形状，不应把库 statement 改成字面量 `4` / `1`。
- `sizeof(PTR)`、pointer store 的大小、alignment 和地址空间上界由当前 `Arch` 决定。
- 旧 proof 如果确实依赖 32 位语义，应显式使用 32 位兼容 lemma，而不是依赖全局 hardcode。

## 1. `sizeof(PTR)` 由当前 CRules 决定

现在只有一个名字：

```coq
sizeof_front_end_type
```

但它来自当前导入的 notation/rules module：

```coq
Import naive_C_Rules.    (* 32 bit *)
Import naive_C_Rules64.  (* 64 bit *)
```

因此：

```coq
sizeof (PTR) = 4
```

只在 32 位 rules 下成立；64 位 rules 下应为：

```coq
sizeof (PTR) = 8
```

推荐迁移：

```coq
change (sizeof (PTR)) with ptr_size_Z.
fold_arch.
```

`fold_arch` 用来把 proof state 中可能出现的 `Arch32.ptr_size_Z` / `Arch64.ptr_size_Z` 折回当前 rules 导出的 `ptr_size_Z`，方便 `PtrArray`、`StoreAux` 等 lemma 匹配。

## 2. 旧的 pointer-uint 等价需要显式 32 位假设

以前固定 32 位时，pointer store 经常可以直接当成 4 字节 unsigned int store 使用。现在这些 lemma 分为 generic 和 32 位兼容两类。

旧 proof 常见写法：

```coq
apply store_ptr_align4.
apply undef_store_ptr_align4.
apply store_ptr_store_uint.
rewrite sizeof_ptr.
```

迁移到 arch-generic 时优先使用：

```coq
apply store_ptr_align.
apply undef_store_ptr_align.
change (sizeof (PTR)) with ptr_size_Z.
fold_arch.
```

如果 proof 本身就是 32 位 case，可以使用兼容 lemma：

```coq
ptr_size_eq_4
ptr_size_Z_eq_4
addr_max_unsigned_eq_int
store_ptr_align4_32
undef_store_ptr_align4_32
store_ptr_store_uint_32
```

## 3. 地址合法性上界从 `Int.max_unsigned` 参数化为 `addr_max_unsigned`

地址空间上界不再全局固定为：

```coq
Int.max_unsigned
```

而是：

```coq
addr_max_unsigned
```

32 位 proof 中需要回到旧形状时使用：

```coq
rewrite addr_max_unsigned_eq_int.
```

或者直接：

```coq
solve_arch.
```

通用 proof 中推荐使用：

```coq
unfold_arch.
solve_arch.
```

它们处理 `ptr_size`、`ptr_size_Z`、`ptr_align`、`addr_max_unsigned` 等 arch 字段的展开和简单算术目标。

## 4. `CNotation` 不再全局导出 32 位 `sizeof`

`sizeof_front_end_type` 和 `sizeof(...)` notation 现在位于：

```coq
CNotationSig Arch
```

需要 notation 的 module 应显式包含对应 rules 或 notation sig。不要在全局环境中 `Include CNotationSig Arch32`。

推荐导入顺序：

```coq
From SimpleC.SL Require Import SeparationLogic.
Import naive_C_Rules.
From SimpleC.EE Require Import xxx_goal.
```

若 goal 文件自身使用 `sizeof(...)`，也应在 goal 文件内部先导入对应 CRules。

`TestNotations` 应保留，并在测试 module 内部显式：

```coq
Include CNotationSig Arch32.
```

这样可以验证 notation/csimpl 正确性，同时不污染全局环境。

## 5. 非 pointer `sizeof` 的 proof-local 形状问题

这次改造不应改变 `ArrayLib` 中非 pointer 类型的 statement 形状。例如：

```coq
(p + i * sizeof (INT)) # Int |-> v
```

应继续保持为 `sizeof(INT)`，不要把库定义改为：

```coq
(p + i * 4) # Int |-> v
```

不过某些 preprocessing tactic 之后，当前 proof state 中可能出现字面量地址：

```coq
(p + i * 4) # Int |-> v
(p + i * 4) # UInt |-> v
(p + i * 1) # Char |-> v
```

而 `IntArray` / `UIntArray` / `CharArray` 的 lemma 仍按 `sizeof(...)` 形状匹配。这种情况只应在 proof 局部折回：

```coq
replace (p + i * 4) with (p + i * sizeof (INT))
  by (rewrite sizeof_int; lia).

replace (p + i * 4) with (p + i * sizeof (UINT))
  by (rewrite sizeof_uint; lia).

replace (p + i * 1) with (p + i * sizeof (CHAR))
  by (rewrite sizeof_char; lia).
```

这类修复只改变当前 proof state 的匹配形状，不改变库导出的 statement。

## 6. 常见迁移 mapping

| 旧 proof 形态 | 新 proof 形态 |
| --- | --- |
| `rewrite sizeof_ptr` | `change (sizeof (PTR)) with ptr_size_Z; fold_arch` |
| `store_ptr_align4` | generic: `store_ptr_align`; 32-bit: `store_ptr_align4_32` |
| `undef_store_ptr_align4` | generic: `undef_store_ptr_align`; 32-bit: `undef_store_ptr_align4_32` |
| `store_ptr_store_uint` | 32-bit: `store_ptr_store_uint_32` |
| `Int.max_unsigned` 作为地址上界 | `addr_max_unsigned`; 32-bit 用 `addr_max_unsigned_eq_int` |
| 手动展开 `ptr_size = 4` | `ptr_size_eq_4` 或 `ptr_size_Z_eq_4` |
| arch 字段展开/算术 | `unfold_arch` / `solve_arch` |
| goal 中 `p + i * 4` 但 lemma 期待 `sizeof(INT)` | proof-local `replace ... by (rewrite sizeof_int; lia)` |

## 7. 验证建议

修改 proof 后至少检查：

```text
make Rocq/CNotation.vo
make Rocq/SeparationLogic.vo
make test/arch64_test.vo
make
```

其中 `test/arch64_test.v` 应覆盖：

- 32 位默认 `naive_C_Rules` 下 `ptr_size_Z = 4`
- 64 位 `naive_C_Rules64` 下 `ptr_size_Z = 8`
- `sizeof(PTR)` 在 64 位下等于 8
- pointer array/store alignment 使用 `ptr_size_Z` 而不是硬编码 4

## 8. 先重新生成，再修复 manual proof

升级 binary 后，应先用与项目一致的参数重新生成 strategy、definition、goal、auto proof 和 check 文件，再处理 manual proof。generated files 是最新接口的依据；如果直接在旧 goal 上修 proof，最终结果可能无法通过完整生成链路。

推荐顺序：

1. 先保存或提交现有的 manual proof 和自定义 proof library。
2. 使用新 binary 重新运行该 case 的完整生成命令。
3. 编译该 case 对应的完整 target，记录第一个真实失败。
4. 只修改 `*_proof_manual.v`、必要的 `*_lib.v`，或在确认生成身份错误时修改 C annotation。
5. 每次修复后重新运行同一个完整 target，直到 strategy check 与 VC check 都通过。

不要手工修改以下文件来隐藏接口变化：

```text
*_goal.v
*_proof_auto.v
*_goal_check.v
*_strategy_goal.v
*_strategy_proof.v
*_strategy_goal_check.v
```

这些文件下一次生成时会被覆盖，也无法代表其他用户使用最新 binary 时看到的结果。

## 9. 先判断当前 goal shape，再迁移旧 tactic

solver 和 preprocessing 更新后，数学结论通常没有改变，但 goal 可能已经被化简。开始复用旧脚本前，应查看当前 proof state 属于哪一类。

### 9.1 纯命题目标

如果 RHS 已经收缩为纯 proposition，旧 proof 中的 `Exists`、`cancel`、`split_pure_spatial` 通常已经多余。先运行项目使用的 preprocessing tactic，再直接证明剩余命题：

```coq
Proof.
  LLM_pre_process ltac:(int_auto).
  (* apply / exact / lia / local lemma *)
Qed.
```

不要为了保留旧的 separation-logic 脚本而把纯目标重新展开成空间目标。

### 9.2 仍含资源的空间 entailment

如果目标仍然包含数组、store、predicate 或其他空间资源，则保留 witness 选择与资源消去步骤：

```coq
Exists current_state.
split_pure_spatial.
- repeat cancel.
- split_pures; dump_pre_spatial; auto; try lia.
```

具体 witness 和 bullet 顺序必须以当前 goal 为准，不能机械复制旧 proof。

### 9.3 preprocessing 已经闭合目标

如果编译报 `No such goal`，通常表示前面的 preprocessing、`cancel` 或 arithmetic tactic 已经完成证明。删除其后的多余 `subst`、`rewrite`、`split_pures`、`dump_pre_spatial` 或 `lia`，让 proof 在第一次闭合处结束。

## 10. 缺失或重复的 proof field

binary 更新可能改变 auto/manual 的分工。遇到 `VC_Correct` field 错误时，先检查当前 generated interface，再决定是否需要新 proof。

### 10.1 field missing

按以下顺序处理：

1. 在当前 `*_goal.v` 中找到 witness 的完整定义。
2. 同时搜索 `*_proof_auto.v` 和 `*_proof_manual.v` 是否已导出同名 `proof_of_...`。
3. 只有 auto 和 manual 都没有该 field 时，才在 manual 中补充同名 lemma。
4. 从当前 witness 的 top-level goal 开始证明，不要通过展开 witness 自身绕过生成接口。

```coq
Lemma proof_of_example : example_wit.
Proof.
  (* start from the current generated goal shape *)
Qed.
```

### 10.2 field already declared

这通常表示 auto 与 manual 同时导出了同名 proof。若 auto 已经提供该 field，应让 auto 保持 ownership，并删除 manual 的重复导出。需要保留旧证明作为迁移参考时，可以注释整个原 lemma，但不要把它改名成 `_manual` 后继续导出。

```coq
(* Now exported by the generated auto proof.
Lemma proof_of_example : example_wit.
Proof.
  ...
Qed.
*)
```

## 11. binder、hypothesis 与 split 顺序变化

新的 preprocessing 可能删除不再需要的空间变量、提前 `subst` 临时值，或调整 split 后的子目标顺序。因此：

- 按当前 `*_goal.v` 的 binder 顺序编写 `intros`，不要假设 left/right branch 仍拥有相同变量。
- 尽量依赖 hypothesis 的含义，而不是固定的 `PreH1`、`PreH2` 编号。
- 每个 split goal 独立建立所需的局部事实；不要依赖前一个 bullet 中的 `assert` 会出现在后一个 bullet。
- 当多个纯目标只是顺序变化时，使用能按目标形状收敛的 tactic，而不是固定顺序的 bullet 脚本。

例如：

```coq
split_pures;
  try (dump_pre_spatial; assumption);
  try (dump_pre_spatial; lia).
```

只有在所有分支使用同一套安全 tactic 时才使用这种写法；关键结构性目标仍应使用明确的 bullet 和对应 lemma。

## 12. 对规范化表达式做 proof-local 修复

新 goal 可能把旧 proof 中的逻辑变量展开成长度、绝对值、位运算、`sublist` 或 `Znth` 表达式。优先利用 generated hypotheses 在 proof 局部恢复稳定形状，不要修改库 statement 或 generated goal。

常见方法：

```coq
rewrite <- Hlogical_name.
```

```coq
replace generated_expr with normalized_expr by lia.
```

```coq
assert (Hbound : 0 <= normalized_expr < limit) by lia.
```

对于 `Znth`、`sublist`、`replace_Znth` 和 setoid rewrite 混合的目标，应先在局部 `assert` 等式或界限，再只改写需要的子表达式。避免大范围 rewrite 引入新的 evar 或改坏无关子项。

## 13. 区分 annotation/generation 问题与 proof 问题

如果当前 goal 中本应相同的逻辑对象具有不同 identity，或必要的不变量根本没有出现在 precondition 中，manual proof 通常不是正确的修复位置。

先检查：

- call-site 的 `Given` / `where` 是否把 caller 与 callee 变量正确关联；
- regenerated hypothesis 与 target 是否引用同一个 logical id；
- strategy 是否把下一条语句需要的事实过早消去；
- 当前 spec 或 proof library 是否确实暴露了目标所需的不变量。

例如 caller 和 callee 都使用名字 `x` 时，不要写含义不清的 `where x = x`；应先固定 caller 侧的 identity，再传给 callee：

```c
/*@ Given caller_x from x */
/*@ ... where x = caller_x */
```

修改 annotation 或 strategy 后，必须重新生成 goal 和 auto proof。不要在 manual proof 中补一个偶然成立的等式来掩盖错误的 symbolic-execution identity，也不要用 `Admitted` 或新增公理伪装接口已经恢复。

## 14. 编写对 binary 更新更稳健的 manual proof

迁移 proof 时建议遵守以下规则：

- 不要在 proof 开头 `unfold` 正在证明的 witness 名称；从当前 top-level goal shape 出发。
- 对结构性目标显式调用对应 lemma，避免用宽泛的 `try`、`auto` 或 `eauto` 猜测关键证明。
- 对大型 `lia` / `nia` 目标先建立局部 bound、等式或分段 lemma，减少巨大 proof term，特别是在 Windows 环境中。
- 先消去空间资源，再对纯命题使用 `dump_pre_spatial`；如果目标仍是空间 entailment，优先使用 `cancel`、空数组正规化或对应的 separation-logic lemma。
- 对顶层 proposition disjunction 使用 Coq 的小写 `left` / `right`，避免与局部导入的 separation-logic tactic 名称混淆。
- 只有在当前 goal 确实需要时才改变 proof；已经通过完整 target 的 manual proof 不需要为了统一风格继续重写。

## 15. 完整验证迁移结果

单个 lemma 可编译只说明局部 proof 成立。完成 port 后，应运行项目为该 case 提供的显式完整 target，并确认以下链路全部通过：

1. C annotation 与 strategy 重新生成；
2. strategy goal、proof 和 goal check；
3. VC goal、auto proof、manual proof 和 goal check；
4. 该 case 依赖的自定义 proof library；
5. 项目要求的目录级或全仓库 build。

若默认 `make` 因缓存或时间戳立即返回，应运行明确的 case 或目录 target；需要排除旧产物影响时，再执行项目支持的 clean rebuild。

最终检查：

- generated files 均来自同一版本 binary；
- 没有通过修改 generated goal/check 文件绕过错误；
- auto/manual 不重复导出同名 field；
- 没有新增 `Admitted` 或未声明的公理；
- architecture-specific proof 只在确实需要时使用兼容 lemma。
